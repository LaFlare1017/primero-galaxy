# Primero Galaxy

**The AI Transformation Maturity Galaxy**: an explorable 3D galaxy where every star is a real Fortune 500 enterprise, every constellation is a transformation strategy, and every trajectory is a path to AI maturity. Built as an Awwwards-level data visualization: the galaxy *is* the interface.

Real companies. One universe. Explore.

## Features

- **Fortune 500 3D galaxy**: instanced `IcosahedronGeometry` rendering of ~193 curated enterprises with per-star maturity color (orange → amber → teal), bloom post-processing, and static dust particles for parallax depth.
- **Force-directed layout**: `d3-force-3d` positions companies so same-industry companies cluster and high-maturity leaders repel; the layout is pre-computed and served by the API.
- **Camera as spacecraft**: `camera-controls` with smooth inertia: drag to orbit, scroll to dolly, double-click a star to fly to planet view, `Esc` to return.
- **Hover → tooltip**: raycaster-driven hover shows company, industry, and maturity score in a cursor-following glass tooltip.
- **Planet view**: camera flies in, the star scales up with orbital rings, and a slide-in panel shows the full maturity breakdown: overall score, 5-dimension radar chart (SVG), animated dimension bars, and transformation trajectory with EBITDA impact, exit multiple, holding-period reduction, and milestone timeline.
- **Trajectory paths**: violet Catmull-Rom splines draw from a company to its projected future state in 3D space.
- **Add Your Company**: a minimal form (name, industry, AI status slider) places a new persistent star in the galaxy, saves it to `localStorage`, flies the camera to it, and offers a trajectory prompt. User stars can be removed from the galaxy with a two-step confirm and an Undo toast.
- **Company search**: a search palette in the galaxy: type a name and fly straight to the star, with keyboard navigation (arrows + Enter) and results for both dataset and user-added stars.
- **Toast system**: added/removed notifications survive a refresh (sessionStorage) but keep only their remaining window; expired toasts never resurrect.
- **Landing sequence**: staggered star appear, title fade in/out, bottom bar with mode indicator (Galaxy / Constellation / Planet) and star count.

CI also enforces the Lighthouse accessibility/SEO scores (currently **100/100 on both routes**) via `scripts/lighthouse-gate.mjs`; the gate fails the build on any regression.

A tracked path that a `.gitignore` rule also covers is invisible in both places you would look for it — `git status` says nothing, because the file is committed, and the rule reads as though the path were never meant to be here — so `scripts/gitignore-gate.mjs` asks `git check-ignore` about every tracked file and fails naming the path and the rule that shadows it. It counts only the `.gitignore` files committed here (your own global excludes are yours) and treats a `!` re-inclusion as the opposite of a violation, which is what git reports for it. It refuses to pass when it has nothing to read, and runs a fixture that plants a tracked, ignored file and must catch it. `node scripts/gitignore-gate.mjs --fix` writes that repair instead of naming it: a `!` negation for the path that belongs in the repo, and, where the rule excludes a whole directory, the rule globbed to `dir/*` first — git never looks inside an excluded directory, so `dir/` plus `!/dir/keep` re-includes nothing at all. Which shape a rule needs is not reasoned about, it is TRIED: each candidate goes into a scratch repository holding the committed rules and the tracked path, and only one the gate then reports clean is written. The scratch copy runs the rules as they are first and refuses the whole thing if that does not reproduce the complaint, so a plan cannot be accepted by a fixture that was already passing. Then, in the order the reader needs: the plan, git's own diff of the change, the write, and a read-back of both gates — this change alters what git ignores, which is the one thing the untracked gate above exists to have an opinion about. Anything the read-back rejects is undone, so `--fix` ends with the file repaired and proven or with the file byte-for-byte as it was, since a half-repair — some rules narrowed and the gate still failing — is worse than no repair at all. `node scripts/gitignore-gate.mjs --fix --dry-run` is that same plan and that same diff, shown and then not written: nothing is written, so there is nothing to read back, and the run says that rather than reporting a repair it did not make — it still exits non-zero, because the paths it found are still covered, and a dry run that exited clean would be indistinguishable from a repair to anything scripting it. `--dry-run` on its own is refused rather than silently promoted, since a plain run already prints the report without writing. The preview is held against the write on every run, because a dry run describing a different repair is the one thing it must not be: the dry run's plan and its diff have to be the write's own, and the lines its diff adds have to be the bytes the write appends. Both halves are proved on every run — as is `preview`, the one function both gates write through, whose own fixture lives with it in `scripts/ignore-file.mjs` and is asked for by both gates, because a fault in it would arrive at both at once: a preview that wrote when it was asked for the diff, printed over the report it is part of, or left git's own two blob-naming lines in the diff, is refused where it lives, and not only by whichever gate happened to exercise it — and a checkout without the other gate's script is told so rather than told a gate passed. The same check runs at commit time through the tracked `.githooks/pre-commit`, which calls `node scripts/doctor.mjs --fast`: opt in once per clone with `npm run hooks:install`, which points `core.hooksPath` at `.githooks/` **instead of** `.git/hooks/` (undo with `git config --unset core.hooksPath`), and `git commit --no-verify` skips it for one commit. The config write goes through `scripts/local-config.mjs`, which reads a key before claiming it and reports — rather than replaces — a value that is already there: a `core.hooksPath` of somebody else's, possibly one from the global config where it governs every repository on the machine, is named with its origin and left alone until `--force`. Because that directory is replaced rather than extended, the installer refuses while a hook git would actually run already sits in the directory it is about to shadow — it names the files and `npm run hooks:install -- --force` installs anyway. The `*.sample` templates `git init` leaves behind are not hooks and are not counted, so a fresh clone installs without ceremony. CI runs `node scripts/doctor.mjs --strict`, which reaches the hook check (`scripts/hook-check.mjs`) itself, twice: once on the checkout, and once against a rule planted in the working `.gitignore` that the hook has to refuse — the second run is the one that tells a hook which checks something apart from a hook which was emptied in a refactor, or which quietly lost its executable bit, since both of those pass a plain run by doing nothing at all. The plant is removed with its original bytes and read back to prove it. Before either run it also asks git which mode it has *recorded* for the hook — `100755` in the index and in HEAD — because that, and not the bit on the machine that made the commit, is what every clone checks out: a hook can look perfectly executable where it was written and arrive dead everywhere else, with `git status` showing nothing at all.

The same contradiction seen from the other side — a generated or vendored path no rule covers, which every `git status` lists again and only somebody remembering not to type `git add -A` keeps out of a commit — is `scripts/untracked-gate.mjs`. It starts from the untracked list `git status` itself shows and requires each path to carry its own evidence rather than consulting a list of paths kept in step by hand: a name a **tracked** lockfile declares as an installed copy (`skills-lock.json` here, the same shape as `package-lock.json`/`node_modules`), the markers of somebody else's project (`package.json`, a lockfile, `.github/`, `.husky/` — a vendored copy), a directory name this repo already ignores elsewhere (`dist`, `out`, `test-results`, the rule that exists but does not reach a second location, which is the mistake b9ae9de fixed for `node_modules`), a megabyte of untracked render output, or a `do not edit` header in a file's opening lines — and only there, since prose *about* generated code mentions the phrase too. Everything else untracked is reported and left alone: a new source file is a decision in progress, and a gate that failed on one would be switched off within a day. It prints the rules that cover each family, in the form that does not contradict the gate above — `dir/*` plus a negation for the copies that belong, because a negation inside an ignored directory is never reached — which is how two tracked skill packs keep their place while the thirteen installed beside them stop being noise. `node scripts/untracked-gate.mjs --fix` writes those lines rather than printing them, and shows the diff before it writes — git's own diff, of the real file against a draft — then reads the result back: the audit has to come clean and the gitignore gate has to still pass, because the two argue about this one file and a fix that satisfied one by breaking the other would be worse than none. It refuses to append a line `.gitignore` already has: if every line is there and the paths are still uncovered, something later in the file — a `!` negation, usually — is undoing them, and a second copy would be undone identically. `node scripts/untracked-gate.mjs --fix --dry-run` stops after the diff: nothing is written, so there is nothing to read back, and the run says that rather than reporting a repair it did not make — it still exits non-zero, because the paths it found are still uncovered and a dry run that exited clean would be indistinguishable from a repair to anything scripting it. `--dry-run` on its own is refused rather than silently promoted, since a plain run already prints the report without writing. It has no CI step of its own: a fresh clone has nothing untracked, and a check that cannot fail on CI is a reassurance rather than a check — it reaches CI the way every other one does, through `npm run doctor`.

`npm run doctor` answers, in one pass, the questions a checkout can answer about itself: that dependencies are installed, that the Node major matches the one the workflows declare, that `.env.local` exists, that the gitignore gate is clean and no generated or vendored path is unaccounted for, that the commit-time hook is installed (executable *here* and recorded as executable in git, since the bit on a machine is not the bit a clone inherits — git *ignores* a hook without it, printing a hint and carrying on, so a lost mode turns the gate off in silence), that nothing else is recorded executable — that same bit read from the other end, refused on every tracked file except the hooks git runs and the two scripts this repo runs by path (`delegate/scripts/reset.sh` and `delegate/scripts/snapshot.sh`, which the handoff invokes as `./scripts/reset.sh` and which are named in the check because nothing here discovers an invocation: a bit on a file nothing executes buys nothing and is a difference the next reader has to explain, which is what two scripts under `scripts/` were at 100755 for) — read from the index, where a stray bit is refused, and from HEAD, where the same bit warns instead, because a bit HEAD records and the index has dropped is a repair somebody has already staged, and the commit that lands it must not be refused for the state it is in — that every script under `scripts/` which is run as a program still runs when invoked — each one spawned in a repository of its own, seeded with a copy of `scripts/` and run through the system temp directory, so a guard that compared paths literally (the `import.meta.url === pathToFileURL(process.argv[1]).href` that `is-main.mjs` replaced) is caught here rather than in somebody's clone, and so `hooks-install.mjs`, whose job is to change this checkout, changes one that is thrown away — reading the OUTPUT and not the exit code, because a program that exits 0 saying nothing fails there the way a gate that cannot report bad news does: silence is the one answer a skipped entry point and a program with nothing to say give alike — that the nested `delegate/` workspace is built and newer than its sources, and that the numbers quoted in `linkedin/` still agree with the repo. Each of those is its own file under `scripts/doctor/checks/`, default-exporting `{ name, order, commit, proof, run }` — the runner discovers them, so a new invariant is a new file rather than a new entry in a list, and where a check reads in the report is stated in the file that knows why. What discovery costs is paid back where it matters: a module that is not a check, two checks sharing a name, or a `checks/` with nothing in it are refused loudly rather than quietly skipped, because a doctor that runs no checks prints exactly what a doctor that found nothing wrong prints. It is the single entry point the repo's checks are wired to: CI runs `node scripts/doctor.mjs --strict`, and the commit-time hook runs `node scripts/doctor.mjs --fast` — the subset whose subject is the commit in progress, the paths it would carry and the hook it would carry, asked about the index rather than about the machine. It reports and repairs nothing: every fix is printed as the command that performs it. A warning is a state this repo treats as a choice — an uninstalled hook, a missing `.env.local`, an unbuilt workspace — so it leaves the exit code clean; `--strict` exits non-zero on those too, which is why the checks that *are* that choice on a fresh CI checkout (no `.env.local`, no hook installed, no `delegate/` build) say so there and stand down rather than warn. `--fast` is deliberately narrower than "everything quick": `untracked` reports on paths the commit does *not* contain, and it is red today on artifacts nobody has ruled on yet, so a hook that refused every commit until that was settled would be switched off within a day. The one check that reads history rather than the working tree is the LinkedIn one: the assets quote an era bounded by two declared commits instead of counted to `HEAD`, so the number a commit carries is the number the commit after it reads — which is why that check can be a CI gate at all, and why the checks job fetches the full history rather than git's default one-commit clone, since a checkout that cannot see the era is told its history is missing rather than told the copy drifted. Every check also carries the levels it claims it can report, with the fixture state that makes each one happen, and a run builds those fixtures before it believes anything: throwaway checkouts in the system temp directory, `git init`ed where a check puts real questions to git, discarded afterwards. Each check then has to answer as it claims — so a check that has quietly stopped being able to report bad news fails the run that was counting on it, and the proof section says which claim did not hold. A check with no proof at all, and a check whose claims are all `pass` and `skip`, are refused the same way: a check that cannot report bad news can only report good news, which is what a check that never looked reports too. The one run that skips the proof is `--fast`, where a commit is waiting and dozens of processes is a cost nobody agreed to pay — `--prove` asks for it anyway, and because it is part of every other run, the CI step proves the whole set on the same commit the hook gated. One more rule: a check that cannot run is a failure rather than a pass, and `scan`, the hook resolver, the hook check and the reader of git's recorded modes — `ls-files -s` and `ls-tree`, parsed and interpreted for every caller in `scripts/recorded-modes.mjs`, because the modes check asks about every path in the tree and the hook check asks about one, and that parse is not worth having twice — are imported from the scripts that own them rather than re-derived, since a second opinion about an invariant is a second thing to keep in sync.

On CI (`retries: 2`, `trace: on-all-retries`), a flaky test **passes** the job — so the run is followed by `scripts/flaky-report.mjs`, which parses the JSON report and writes the flaky table (test, attempts, first-failure point) into the job summary and exposes a `flaky_count` output: the flake rate is a visible metric, never silently absorbed. Report and retry-attempt traces upload on every run, green or not. Locally the suite runs with `retries: 0` — a flake is a failure you see immediately, and the deterministic patterns in `e2e/cmdk.ts` exist precisely to keep it rare.

### The data-table-filter engine (`components/data-table-filter/`)

A subject → operator → value filtering system for any tabular dataset, split into a headless core and a rendering layer:

- `core/types.ts` — the model: `FiltersState` is an array of `FilterModel`s (`{ columnId, type, operator, values }`) with a typed operator vocabulary per column kind (`text` → contains, `number` → is between, `option` → is/is not, …).
- `core/filters.ts` — `createColumnConfigHelper<T>()`, a fluent builder that infers accessor value types; `createColumns()` derives memoized option/facet getters and prefetch hooks from your data.
- `hooks/use-data-table-filters.tsx` — the headless hook: returns `{ columns, filters, actions, strategy }`; controlled (`filters` + `onFiltersChange`) or uncontrolled (`defaultFilters`). `strategy: 'server'` swaps client-derived options/counts for server-provided ones via the `options`/`faceted` inputs.
- `components/` — the `DataTableFilter` UI: a cmdk Filter popover (subject → operator → value), active-filter chips with ✕ removal, a Clear-all action, and a mobile layout. `lib/filter-fns.ts` holds the pure predicates; `lib/i18n.ts` + `locales/en.json` label the operators.

FinBench wires it to the run-records table (from `components/finbench/`):

```tsx
// 1. Describe the filterable columns (type-safe, inferred accessors).
const dtf = createColumnConfigHelper<FinbenchRunPublic>();
export const runFilterColumns = [
  dtf.option().id('result').accessor((run) => runResultKind(run))
    .displayName('Result').icon(CheckCircle2)
    .options([{ value: 'miss', label: 'numeric miss' }, …]).build(),
  dtf.number().id('groundedness_score').accessor((run) => run.groundedness_score)
    .displayName('Groundedness').icon(Gauge).build(),
  // … text, number, and option columns
] as const;

// 2. Drive the hook from URL state and render the UI.
const urlState = useRunFilterState();                       // nuqs ?filters=…
const { columns, filters, actions, strategy } = useDataTableFilters({
  strategy: 'client',
  data: runs,
  columnsConfig: runFilterColumns,
  faceted: runFacetedOptions(runs),                         // option → count map
  filters: urlState.filters,
  onFiltersChange: urlState.setFilters,                     // controlled
});

<DataTableFilter columns={columns} filters={filters} actions={actions} strategy={strategy} />

// 3. Apply the same state to your rows with the pure predicates.
const visible = applyRunFilters(runs, filters);
```

Filter state is URL-synced through nuqs under a single `?filters=` param (a JSON-serialized `FiltersState`, validated on parse — garbage degrades to the unfiltered view), so any filter combination is a shareable deep link, e.g. the one numeric miss in the published ASC 606 snapshot. The run table's column sort rides alongside as `?sort=`/`?dir=` (nuqs, `clearOnDefault` against task/asc — same shape as the facilitator console), so a sorted view is shareable too and a saved view replays into exactly the view it was saved from. Two conventions make this work with static prerendering: the nuqs-backed page is wrapped in `<Suspense>` (URL readers force a client bailout), and an empty filter list is stored as `null` so the param disappears entirely instead of rendering `?filters=`.

### Command palette (`components/ui/CommandPalette.tsx`)

A ⌘K / Ctrl+K palette mounted once in the root layout, so it works on every surface. It has three internal routes — navigation, every published FinBench task, and Delegate scenarios — driven by a `route` state (Esc or Backspace-on-empty walks back to root):

```tsx
<CommandItem onSelect={() => goScenario(scenario.id)} keywords={['workshop', 'delegate']}>
  <ClipboardList className="text-muted-foreground" /> {scenario.title}
</CommandItem>
```

Selecting a Delegate scenario is context-aware: from another page it deep-links `/delegate?scenario=s5`; from `/delegate` itself (already mounted, a query push would not re-render it) it dispatches the `delegate:select-scenario` CustomEvent that the page listens for. Both paths converge on one writer: `?scenario=` is a controlled nuqs param on the page (`parseAsStringEnum` over `s1`–`s6`, `clearOnDefault("s1")`, `<Suspense>` wrapper), the same writer the landing screen's scenario cards share — so the URL can never silently diverge from the selection (an earlier read-once parse left a stale param that a refresh re-applied), and an unknown value degrades to the default instead of breaking the page.

### Saved views (`components/finbench/saved-views.ts`)

Circle's named-views pattern adapted to FinBench: the current filter combination can be saved under a name and re-applied later. The store keeps the **engine-native `FiltersState`** (not a declarative copy), so applying a view replays through the identical nuqs pipeline as a hand-built filter or deep link. Persistence follows this repo's convention — plain `localStorage` (one namespace per benchmark track) with a `finbench:saved-views-changed` CustomEvent for same-tab updates and the `storage` event for cross-tab sync, instead of Circle's `zustand/persist`:

```ts
saveView({ name: 'Numeric misses', track, filters, description: describeFilters(filters) });
listSavedViews(track);   // sorted by name; corrupt rows are dropped, never thrown
deleteSavedView(view.id);
// Applying a view = feeding its engine-native filters back to the URL state:
onApply(view.filters);   // → nuqs setFilters → same ?filters= pipeline as a deep link
```

The `SavedViews` popover (bookmark trigger next to the filter bar) marks the active view — the one whose filters JSON-match the live state — with a check, and disables "Save current" until a filter exists.

The popover UI itself is shared: `components/ui/SavedViewsPopover.tsx` is generic over a small store contract (`list`/`save`/`update`/`remove`/`isActive`/`apply`/`describeCurrent`/`canSave` plus the store's write-event name, and an optional `shareUrl`) and a `mono` tone for Delegate's monochrome chrome. Views carry an emoji chip (a 14-icon palette Circle-style) and can be renamed or re-iconed after saving: the edit form reuses the save form prefilled and submits through `update()`, leaving the derived description untouched. When a store supplies `shareUrl`, each row gains a Share button that copies a link to the view without closing the popover. The facilitator console reuses it verbatim (`components/delegate/saved-views.ts`): a view snapshots the selected status facets plus sort key/direction — defaults stored as `null`, mirroring nuqs `clearOnDefault`, so a view replays into exactly the URL shape it was saved from — and sort keys are re-validated against the known set on apply, so a hand-edited store row degrades to the default sort instead of corrupting the URL. Unlike FinBench, the facilitator's default state is savable: a named full-room view is the escape hatch back after facet filtering. It is also the one surface with sharing: Share copies `origin + /delegate/facilitator?status=…&sort=…&dir=…&view=<name>` — the same deep-link shape, plus the view name for the receiver — and opening such a link shows an ephemeral "Opened shared view" toast, strips the `?view=` param immediately so a refresh never re-toasts, and leaves the state itself to the ordinary params.

### Surface usage

- **Galaxy** predates the extraction and intentionally does not consume the primitives: its overlays are bespoke (glass tooltip, planet panel, toast stack) and tightly coupled to the 3D scene. It benefits from the token layer and ships the ⌘K palette; its `components/ui/*` remain galaxy-specific.
- **FinBench** is the reference consumer of the full stack: engine + primitives for the run explorer, saved views on top, plus `Table` primitives for the category × model matrix. `RunsTable` is the canonical wiring example.

### Conventions for new surfaces

- Compose from `components/ui/primitives/*` and the engine before reaching for bespoke UI; style with token classes (`bg-popover`, `text-muted-foreground`) so both chrome modes work.
- Need a ref into a primitive (autofocus, scroll-into-view)? The primitive must be `forwardRef` — check before relying on it; React 18 silently drops refs on plain function components.
- Popover/dialog content is portaled and `position: fixed`: it re-anchors on scroll events, so open it from settled positions (or pass `updatePositionStrategy="always"` to re-anchor every frame) and drive it with the keyboard in e2e — pointer clicks on off-screen fixed content cannot be scrolled into view and hang.
- cmdk lists (⌘K palette, FinBench filter popover): Enter activates whatever is highlighted at keypress time, and a controlled search must round-trip through React state before the list reflects it — so a keyboard-driven test drives the selection, not the search: `selectCmdkItem` in `e2e/cmdk.ts` arrows until the target row is selected (`[cmdk-item][data-selected="true"]`, in a retry loop) and presses Enter. Pointer clicks on items are always safe (items own their click handlers); the palette spec relies on this.
- Wrap any page reading URL state in `<Suspense>`; store client-only persistence in a `components/**` module with a change event, mirroring `saved-views.ts`.
- Global keyboard shortcuts go through `useKeyboardShortcuts` (`components/delegate/`), never a hand-rolled window listener: the shared policy keeps them out of text fields, content-editable hosts, and open overlays (a modal, or a popover like the saved-views panel — the panel is portaled and, in Radix 1.1.23, still a `role="dialog"`, so the policy matches both its role and its popper wrapper, and only while it is open), and refuses modified presses (`⌘←` is the browser back gesture). Bindings are keyed by unmodified `KeyboardEvent.key`; a shortcut that genuinely needs a chord composes its own handler on `ownsArrowKeys` instead of widening the policy. Pass `enabled` to mount nothing rather than a listener that would no-op. The policy guards the *sweep*, not the keystroke — a focused field still receives its characters, which is what makes a bare-letter binding (`j`/`k` on the grid) safe to have. A shortcut that needs two keys (the grid's `g i`/`g n` jumps) goes through `useKeySequence`, which layers the same policy on the whole chord, never consumes a key it does not own — so an unbound second key falls through to the binding that does — and lets an armed prefix lapse rather than firing at a letter typed much later. A chord is only honest if the console admits it is half-typed, so `useKeySequence` returns the armed prefix and the surface renders it (the console's chip is a live region, not just a drawing). A keyboard affordance that only moves something visual — a ring, a highlight, `aria-current` — needs a live region too, or it does not exist for half the room; keep the words to the facts that change what a person would do next, and leave ticking values (clocks, countdowns) out, since a region that rewrites every second is one nobody can listen to. Give each fact its own region rather than sharing one, because a status region re-reads its whole text on every change. Prefer a chord to spending a single key that already means something. A shortcut sheet must derive each entry's availability from the same gate expression that mounts its key, or it becomes a list of keys that teach people to press dead ones; a new modal surface needs nothing extra to be safe, because `role="dialog"` is already in the policy. A sheet documents every binding from ONE declaration — single keys and chained ones together, in `components/delegate/consoleShortcuts.ts`, which also builds the key map, the chord map and the aria strings — and the surface supplies only BEHAVIOUR, keyed by binding id. That is what makes the two halves of the drift impossible rather than unlikely: a chord cannot be documented without being bound, because a chord with no behaviour is not in the map and its tests fail; and it cannot be bound without being documented, because the sheet reads the declaration and not the page. A new destination is one row in the declaration plus one behaviour. And none of that is the console's private business: it is a property of any surface that declares its keyboard in one place, so it lives in a harness (`e2e/keyboard-coherence.ts`) that takes a manifest — the declaration plus the readers that interpret it, handed over as they are, so the checks run the shipped code rather than a second copy of it — and asks the same questions of any of them. What the harness cannot know is what a state of a surface can BE, so the manifest declares its independent facts and the invariant that turns a combination into a real state, and the harness owns the product and the filtering: the state space stays the surface's business, the coherence does not. A harness only ever run against one manifest has not been shown to be one, so it is also run against a synthetic keyboard of its own — coherent, then broken once per rule — which is the only place some of the checks can bite at all, since on a module whose readers share one predicate they agree by construction. And a check that walks no state says so instead of passing: an enumeration that came back empty would make every assertion built on it true. A harness is only worth having as far as it GENERALISES, and that costs nothing to check: the ⌘K palette declares its keyboard the same way, in `components/ui/commandPaletteKeys.ts`, and the same harness runs over it in node unchanged — including a surface with no window key map and no chord namespace at all, whose readers are then honestly empty instead of stubbed to look busy. Declaration and use move together: the palette's toggle chord is matched in the component as the row spells it, and its `aria-keyshortcuts` is built from the rows that decide it — so the key a sub-list advertises goes away the moment the field has something for Backspace to delete. Every KEY of every binding is pressed rather than every binding, which is what makes two spellings of one chord (`Meta+k` and `Control+k`) two presses, and what keeps a row with alternatives honest; and each press starts from a state where that binding is live, earned by the surface's own `prepare` where the gate is conditional, so a step that needs a sub-list says it started in one. A key that does nothing fails under the name it was declared by, and the half of a toggle that CLOSES is covered by the same rule — the half nobody writes a feature test for. One promise is not about a single declaration at all: a binding owned by a component elsewhere is declared TWICE — by the surface that binds it, and by a surface that only documents it, which is what `mount: 'global'` means on both sides — and neither declaration can see the other. So the two are compared field by field, from the declaration rather than from the running app: keys as a SET (the order a surface lists alternatives in is a rendering choice), the gate, what it stands down for, the mount and the yields, while ids, labels and display strings stay out of it, because those are how each surface speaks to its own readers. The pairing itself is stated and pinned, since two ids for one key have nothing in common to match on, and the check found the first real disagreement it was written for: the console's sheet documented the palette's `⌘K` while the palette also answered `Ctrl+K`. The row now names both spellings, the console's coverage spec presses both — a row with two spellings owes two presses — and the sheet still prints one cap, because the label already names the PC key in words. Two more surfaces are declared on the same terms, and between them they add the two shapes the first three did not have. The galaxy's search field PRINTS a key it does not bind — Esc belongs to the page's own overlay priority (the search, then the add form, then the selection), so that row is `global` while the field renders the `esc` cap from it, because a hint is a claim too and one typed into the JSX is a claim nothing can check. The saved-views panel is the first whose Escape is LAYERED rather than allowed: the form's Escape steps back to the list and only the list's Escape dismisses it, so the dismissal lives `under` the form and the declaration shares no key at all — and since Radix dismisses in the capture phase, that form branch has to be taken on the panel's own layer, because a handler on the field it is typed into runs after the panel is already gone. Both also show what the coverage runner is FOR: nothing in the suite pressed the search's ↑/↓, so a walk that had stopped moving would have passed every test the repo had. A field should dispatch the keys it ADVERTISES, as one lookup over the rows the surface claims, so a renamed row stops answering and fails its step instead of going on working while the attribute stops mentioning it. The galaxy page's own dismissal ladder is the third shape, and the first whose bindings are all page-level: three rows on one Escape — the search, then the add-company sheet, then the selection — each answering only while the rungs above it are shut, which is what a LIST of `under` gates says and what the pairwise stack cannot. That needed a collision mechanism the harness did not have, because a row the page binds itself answers from a listener the component wrote: two of them live at once is again whichever listener the browser registered second, and no layer stack can separate rows that nothing mounts. The page then dispatches from the declaration — one lookup for the topmost live rung — so which rung a press reaches cannot differ from the one the checks walked, and the add-company sheet's own Escape listener went away, since a second window listener for one key is a second owner of one press, with nothing to keep the two in order. The ladder is also the agreement check's second client, from the other end of one binding: the field documents the Esc the page answers, and the two agree about the keys, the gate and the mount — a comparison that forced the ladder to name that state the way the field names it, because two declarations describing one binding under two names are disagreeing about it rather than speaking dialects. And emptying a row's keys found the coverage runner's own blind spot one level down: a binding that names no KEY is pressed zero times, so its exercise never runs and the both-directions check cannot see it, since that compares ids — refused now, before a browser opens, which is the same guard the enumeration has for a state walk that came back empty.
- Chrome and content keep to different edges, and the shared number between them is declared once: the galaxy's bottom bar owns its height (`--bottom-bar-h`, `app/globals.css`) and everything that must not cover it offsets by that token — the profile drawer and the toast stack. This is not tidiness. The drawer used to reach `bottom-0` at `z-30` over the bar's `z-20`, so with a profile open all four of the bar's controls were behind an opaque full-height panel: unclickable by pointer, reachable by tab order only, which is a layout bug wearing the costume of a design. It survived as long as it did because it is invisible to every test that clicks the bar BEFORE selecting anything — the state where the bar is still bare — and because its symptom is not an error but a click that retries until it times out. So a control's reachability is asserted the way a pointer asks it (`elementFromPoint` at the control's centre, naming what is in front of it), and the covered control's spec presses it by CLICK rather than by focus + Enter: the keyboard path is what still works when a control is buried, so a step that quietly takes it is the check going quiet.

## How It Works

- **Data**: `/api/companies` serves a curated dataset of ~193 real Fortune 500 enterprises (`lib/fortune500-data.ts`). Each company carries estimated AI-maturity scores (0–100 across five dimensions) plus a researched note on its public AI positioning, compiled from earnings-call commentary, product launches, and reported deployments (research estimates, not audited). Layout positions are pre-computed with the force simulation; 12 AI flagship companies are marked featured.
- **Rendering**: all 500 stars share one `InstancedMesh` (one draw call); per-instance color and scale are set from maturity. Only hovered/selected stars get individual meshes. Dust is a static `Points` cloud.
- **LOD**: labels and constellation lines fade in based on camera distance, so the galaxy stays uncluttered at overview and data-rich up close.
- **Persistence**: user stars live in `localStorage`; pending toasts in `sessionStorage` (survive refresh, die with the tab).

## Reduced motion

The app honors the OS-level `prefers-reduced-motion` setting on three layers:

- **CSS**: a global kill switch in `globals.css` collapses keyframe and transition durations to ~0 (legend bubbles, trajectory breathe, scroll reveals, hover lifts).
- **Framer motion**: `MotionProvider` (mounted in `app/layout.tsx`) wraps the tree in `<MotionConfig reducedMotion="user">`, so every `motion.*` element skips transform animation while opacity fades remain.
- **WebGL / canvas**: react-three-fiber render loops gate themselves through the shared `usePrefersReducedMotion` hook. Idle decoration (galaxy rotation drift, star breathing and flicker, planet spin and moon orbits, ring pulses, auto-orbit, trajectory travel loop, system-map payload dots) is frozen; functional motion (star appear stagger, hover and selection feedback, camera fly-to on selection, zoom-driven fades) is preserved so the scenes stay fully operable as near-static diagrams. The Libraries.dev effects in Delegate (composer beam, thinking orb) unmount instead of animating; meaning is carried by text, borders, and disabled states.

The pass is proven end to end by `e2e/reduced-motion.spec.ts`, which emulates the setting in Playwright: the Delegate working state keeps its live-region status and disabled composer with no decorative canvas mounted, and the Galaxy starfield quaternion is sampled twice and shown frozen while the scene keeps rendering.

## Accessibility

Two automated gates run in CI and fail on regressions:

- **axe-core** (`e2e/a11y.spec.ts`, part of the Playwright suite) scans the WCAG 2.1 A/AA rule tags across all three surfaces — including interactive states, not just loaded routes: the galaxy planet panel and Add-Your-Company dialog, the FinBench Filter popover and deep-linked chip state, and the Delegate workspace while the agent is working plus the seeded facilitator console. Any violation fails the run; new exclusions must be added explicitly (with a justification) in the spec, never silently.
- **Lighthouse** (the `lighthouse` CI job) enforces a 100/100 accessibility + SEO score on `/` and `/galaxy` via `scripts/lighthouse-gate.mjs`.
